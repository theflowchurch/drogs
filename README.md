# Kuriake Castle annual registration

This branch replaces the renewal questionnaire with account-based annual registration, bishop-submitted pastor lists and an Unclaimed review queue. The previous portal remains at `https://jkgbafa.github.io/drogs/` and is preserved on `codex/renewal-archive-2026-09-25` in `theflowchurch/drogs`.

## Current delivery

The live site: **https://kuriakecastle.org/** is a public hero page (castle, name, *Enter the castle*); **/directory/** is the public directory — search, then two doors (Bishops / Pastors with totals), then the cards — open to anyone, showing the existing roster until the office sets **Settings → Public directory shows** to `roll`; **/signup/** is where members sign up or sign in (an unrecognised email is told to create an account) and then see My profile (editable), the Directory and, for bishops, their pastors; **/admin/** asks for the office access code, then an approved office email (Settings → Office emails), then a code sent to that email; `drogs.dagministry.org` redirects there. The product name is Kuriake Castle everywhere a person reads it; internal identifiers and storage keys keep the `drogs` prefix, served by the Hostinger Node.js application from branch `codex/annual-registration` with **MySQL + private Cloudflare R2**. That domain is the canonical address for every link handed out; `APP_URL` must be exactly `https://kuriakecastle.org`. See [HOSTINGER.md](HOSTINGER.md) for the deployment steps and [HOSTINGER.env.example](HOSTINGER.env.example) for all environment variables. The server integration is implemented; production credentials, admin emails, migrations and live connection checks must be completed before rollout.

`https://jkgbafa.github.io/drogs-registration/` now only redirects to the live domain. Hostinger's GitHub integration deploys `codex/annual-registration` automatically on every push (install → `npm run build` → restart `scripts/start-hostinger.mjs`); builds and logs are visible in hPanel or through the Hostinger API (`hosting/v1/accounts/{username}/websites/kuriakecastle.org/nodejs/builds`). The entrance password is still **1234**, on both the portal and `/admin/`. Email addresses select demo accounts; no message is sent and this is not secure authentication. Do not use real registration information in the demo. Demo uploads are stored in IndexedDB, while registrations use `drogs-registration-v1`. Neither the old `drogs-2027` key nor the reconciled legacy source data is read or overwritten by the new flow.

The application starts with **zero registrations**, but not with an empty directory. `src/registration/reference-people.json` (built by `node scripts/build-reference.mjs` from the reconciled rosters) holds the 259 bishops and 5,069 pastors DROGS already knows, with portrait, denomination, city, country, branch and recorded contact details. These are existing records, not registrations: nothing is approved or paid until the person registers. No existing account is silently created or approved.

## Directory

The public **Roll of Good Standing** (member Directory tab and `/directory/`) starts at zero each year and lists only people confirmed this cycle — approved bishops and claimed pastors — with counts of bishops and pastors. It shows name, portrait, title, denomination, city and country; never contact details. Registrants who match an existing record by name are asked *Is this you?* with the old portrait; confirming links the record and pre-fills the form with what Kuriake Castle already holds, so they only correct what changed. The office's **Directory** is the same registered set with full details; **Original data** is the pre-registration roster with the red/green markers. For a registered person linked to an existing record the office chooses which photo the roll shows (new upload or existing).


- **Office Directory** lists every existing record with a Bishops/Pastors switch, organization, denomination and country filters, and an Updated / Not updated / Unclaimed filter. A green dot means the person registered this cycle or their bishop confirmed their details; red means DROGS still holds the older information. The Denominations view opens the bishops and pastors inside each denomination; a bishop’s record opens with the portrait large in the centre, title, country and denomination, and every pastor under that bishop below (this cycle’s confirmed list plus the recorded roster); the previous email or phone is shown next to the confirmed one.
- **Members** who have submitted a registration get a Directory of every bishop and pastor: the same switch and filters, and a record view with the portrait, title, country, denomination and branch, the pastors under a bishop, and a pastor's bishop. Email addresses, phone numbers and dates of birth are stripped before the roster reaches the browser.
- **Verify existing records.** When a bishop pastes their annual list, names that match an existing record appear under *Verify existing records* with the portrait and the recorded email and phone beside the new ones. Confirming from the photo links the list entry to the record and makes the new details current; the older details stay visible to the office. The same record cannot be confirmed for two people in one cycle.
- **Unclaimed** in the Directory filter means an existing pastor whom no bishop has listed this cycle. The Unclaimed queue in the sidebar is unchanged: pastor registrations that do not match any bishop's list.

## Registration and annual lists

- New and returning members enter an email address. Hostinger mode verifies one-time email codes through SMTP and stores accounts in MySQL. The optional Supabase adapter is retained.
- Required details: role, first name, last name, email, phone, date of birth, country, city, organization, denomination where applicable, and an official-attire photo. Pastors type their bishop’s first name and surname (both required, so a single common name cannot be confused); if exactly one approved bishop has that full name, the pastor is placed under them, and the pastor’s own name is matched against the annual lists. While typing their country, the form already shows the annual commitment with an indicative local-currency amount.
- Organizations: First Love, United Denominations, DHMM, FLOW, HJC. In the existing roster, Outreach rows are shown under their group (FLOW office → FLOW, Healing Jesus Council → HJC) and QODESH FAMILY CHURCH is merged into QODESH FAMILY CHURCHES. Sign-up links per role: `/signup/bishop/` and `/signup/pastor/` (role fixed); `/signup/` lets the person choose.
- Drafts can be saved; applicants review details and confirm accuracy before submission.
- The office verifies bishop accounts and optionally links each account to the correct legacy bishop reference. Approval unlocks the bishop’s annual list and $100 USD commitment.
- Bishops upload their pastors as an Excel or CSV file (parsed in the browser with SheetJS) or paste from a spreadsheet: **full name** and **date of birth** written day/month/year, with email and phone as optional extra columns. A bishop can do this as soon as they have submitted; the office confirms, denies or asks them to resubmit (with a note the bishop sees) from Bishop approvals. Bishops appear on the public roll only once confirmed; their pastors appear under them.
- Pastors choose their bishop from bishops who have already registered (the search forgives spelling and word order). A pastor matches that bishop’s list when the name is alike and the date of birth is the same, a day out, or written with day and month swapped — and exactly one entry fits. Otherwise they float in that bishop’s Unclaimed for a photo-confirm. Close spellings, name-only matches and ambiguous duplicates require confirmation.
- Unmatched registrations remain **Unclaimed**, shown in red in their own queue. They never appear in the main Directory until confirmed. Unassigned Unclaimed pastors are visible to every approved bishop; a bishop who confirms one takes them onto their own list, and the office can assign or correct the bishop.
- Confirmed pastors pay **$50 USD**. All commitments are explicitly **non-refundable**, with acknowledgement before payment proof submission. Payment screenshots require office verification; uploading an image never marks a payment as received.
- The payment card shows an **indicative local amount** for the country entered at registration (for example "about GHS 1,150 in Ghana"), using the free `open.er-api.com` USD rates, cached in the browser for twelve hours. It is labelled indicative: DROGS is paid in USD and the bank or mobile-money provider sets the final figure. If the rate service is unavailable or the country is unknown, only USD is shown. `src/registration/exchange.mjs` maps every country in the roster except the ambiguous bare "Congo".
- **Settings (office).** `/admin/` → Settings stores integration values in `dr_config` and layers them over the host environment at runtime, with no restart: Resend API key and From address (mail then goes through `smtp.resend.com`), whether the emailed sign-in code is required, Paystack public/secret keys, Telegram, Cloudflare R2 credentials, and the office/directory access codes. Values are never shown back.
- **Payments** are mobile-money transfers to the number set in Settings (`MOMO_NUMBER`, `MOMO_NAME`); members upload the confirmation screenshot with its Transaction ID, which can only be used once, and the office verifies against the statement.
- **Image storage fallback.** If Cloudflare R2 rejects an upload (wrong credentials, outage), the image is re-encoded smaller and stored in MySQL (`dr_media_blobs`, keys prefixed `db/`) and served through `/api/registration/media/blob` with the same permission checks, so no member is ever stopped by a storage problem. Startup runs the idempotent migrations.
- Receipt uploads pass a **receipt check** (`src/registration/receipt-check.mjs`) before they are stored. It warns when an image looks like a photograph of people or scenery, or cannot be read as a document, but never blocks the upload; the office still verifies every receipt. It is pixel statistics, not OCR, so the office still verifies every receipt.
- **Any issues?** in the corner of every signed-in screen sends a report to the office. On Hostinger it emails `ADMIN_EMAILS` (reply-to the member) and, when `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are set, posts the same text to that Telegram chat; reports are limited to five per account per ten minutes. The browser demo keeps reports locally and says so.
- In the browser demo, an account created on a device is remembered on that device: after the entrance password the member goes straight to their workspace. *Sign out* forgets it; the idle lock does not. On Hostinger the session cookie already does this and a fresh sign-in still requires the one-time email code.
- New MoMo/bank instructions have not yet been supplied. No invented account is displayed. Connected-mode payment uploads remain disabled until `NEXT_PUBLIC_PAYMENT_INSTRUCTIONS` is configured; the demo allows sample receipts.
- Removal requires Transferred, Resigned, Dismissed or Other (with explanation). Records and payments are retained, and removed pastors leave the active directory. Complex reinstatement/transfer corrections should be handled by the office; the present UI does not edit already submitted registration fields.
- Only the office can open the following annual cycle. Historical registration status is preserved; accounts persist; fresh registrations and payment records are required. Prior annual lists and payments are not automatically carried forward.

## Optional Supabase backend (not the Hostinger MySQL setup)

1. Create a Supabase project. Apply `supabase/migrations/202609250002_registration.sql`, `supabase/migrations/202609250003_registration_details.sql` and `supabase/registration-reference-seed.sql`. A fresh registration-only project does not need the older API migration. Neither script erases existing data. The seed contains reference names, titles, organization labels and photo paths, not personal contacts or registrations.
2. Enable email authentication. In the Magic Link template include `{{ .Token }}` to send the one-time code used by this interface. Configure custom SMTP and appropriate delivery limits. Supabase’s default sender only sends to project-team addresses and is not sufficient for public registration.
3. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` to the project URL and public publishable/anon key. Both are required. Never place a secret/service-role key in a `NEXT_PUBLIC_` variable.
4. An office member signs in to create their verified auth user. Add that exact user ID to `registration_office` using the Supabase SQL editor, e.g. `insert into public.registration_office(user_id) values ('VERIFIED-USER-UUID');`. There is no client-side office-role assignment in connected mode.
5. Configure `NEXT_PUBLIC_PAYMENT_INSTRUCTIONS` with confirmed Ghana payment details, then rebuild and deploy. The current static build supports Supabase directly; it does not require a Next.js server.
6. Test OTP delivery, office access, a bishop approval, a pastor registration, an Unclaimed resolution, and a private upload across two devices before rollout.

SQL writes go through `registration_action` with verified identity and role checks. Clients have no direct read/write privileges on registration tables. `registration_snapshot` scopes records to the applicant, selected bishop or office. Private images use a dedicated `registration-media` bucket with 5 MB JPEG/PNG/WebP limits and expiring signed URLs. Only the owner and office can read receipts; the selected bishop can read submitted pastor portraits. Legacy public R2 portraits remain untouched; new private registration images use Supabase Storage to keep authorization enforceable without requiring R2 service credentials in the browser. If its free storage allowance is exceeded, a server-side R2 upload/signing service or a larger storage allowance will be needed.

The entrance PIN is used only in the browser demo. Connected mode starts with verified email sign-in; the URL cannot grant office privileges. Accounts sign out after 30 minutes without keyboard/pointer activity. SQL locking makes roster additions, claims and payment decisions atomic and prevents stale actions from overwriting already completed decisions.

## Develop and verify

```sh
npm ci

NEXT_PUBLIC_REGISTRATION_BACKEND=demo NEXT_PUBLIC_BASE_PATH=/drogs-registration npm run build

# In another terminal, with Python Playwright installed:
```

Browser checks use isolated browser storage and sample accounts, preserving the legacy key. They cover registration/drafts, office bishop verification, roster import, Unclaimed exclusion from Directory, linking spelling differences, payment proof/verification, removal, cycle reset and desktop/mobile layouts. SQL tests assert rejected self-approval, wrong-bishop access, wrong-owner photo uploads, direct table access and unpaid/unauthorized payment attempts.

## Separate preview publishing

The source branch is `codex/annual-registration` in `theflowchurch/drogs`. CI validates it (unit tests, static build, real MySQL integration) and Hostinger deploys the same push to `https://kuriakecastle.org/`. Nothing is published to GitHub Pages any more; `jkgbafa/drogs-registration` holds only a redirect to the domain.

The registration form replaces Church with an organization-dependent Denomination dropdown; its complete choices are in [DENOMINATIONS.md](DENOMINATIONS.md). First Love includes its main church and the six supplied affiliated denominations. DHMM, FLOW and HJC disable and clear the denomination. The review screen places the applicant’s image beside the role-specific example and requires an explicit attire acknowledgement before submission, enforced by both the local model and SQL RPC. Bishops must wear their official red jacket; a collar alone is insufficient. This is a human confirmation, not automated image classification. Historical submitted records remain unchanged.

## Application API keys

Office users can issue scoped, expiring, revocable read-only keys under `/admin` → API keys. Other servers use these to read submitted registrations, annual lists or portraits from DROGS. They cannot change or delete data. See [API.md](API.md) for endpoints and permissions.
